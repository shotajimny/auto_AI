# ヘキサうどん通信・ルール対応メモ

このクライアントが参照した第37回大会の資料と、提供された公式簡易サーバーでの確認内容です。資料に記載された大会運営上の指示は、ソフトウェア実装の参考情報として扱っています。

PDFの古い例では `daySeconds: 5` となっていますが、OpenAPI、後の設定JSON説明、実際の簡易サーバーは**日数と同じ長さの整数配列**を使用します。クライアントは新しい形式を標準にします。状態の `day` は0始まりです（フォーマットPDFの説明に従い、例の `day: 1` を初日と誤解しないでください）。

## HTTP API

HTTP/1.1 を使用します。認証は全APIで `Procon-Token: <token>` ヘッダー、または `?token=<token>` クエリーです。クライアントではURLや履歴へ残りにくいヘッダーを使用します。POSTの本体は `Content-Type: application/json` です。

| メソッド | パス | 要求・応答 |
|---|---|---|
| GET | `/setting` | 初期設定。`startsAt`, `daySeconds`, `daySteps`, `map`, `spots`, `agents`, `fuelLimits`, `players`, `busyThreshold`, `jammedThreshold` |
| POST | `/agent` | 生の整数配列 `[0, 1, 0]`。種類は0=巡回車、1=補給車。成功時はHTTP 200で空の本体 |
| GET | `/` | 当日の `endsAt`, `day`, `agents`, `others`, `traffics` |
| POST | `/` | 生の二重配列 `[[2, -14], [-16], [-16]]`。応答 `{"revision": 1}` |

`revision < 0` は不受理、`revision >= 0` は受理です。HTTP 200だけでは行動受理を意味しません。同じ日の提出では、より大きいrevisionの有効な回答が採用されます。並列送信でも応答が返った順とは限りません。簡易サーバーではrevisionは翌日へも増加しました。日ごとに0へ戻ることを前提にしません。

認証失敗はHTTP 401で `{"code":"AuthError","message":"..."}`、時間外はHTTP 403で `{"code":"AccessTimeError","message":"..."}` です。OpenAPIには記載のないHTTP 400のプレーンテキストエラーも簡易サーバーで確認しました。特に `/agent` の個数不一致では `SubmitKinds: ...` となるため、全応答がJSONとは仮定しません。

### 試合の進行

1. 設定公開後に `/setting` を取得します。開始時刻未確定なら `startsAt: 0` です。
2. 種類の受付中に `/agent` へ全エージェント分を提出します。エージェントの順番は最初の `agents` と共通です。
3. 種類の締切後に `startsAt` が将来の開始UNIX秒になります。この時点では `/` はまだ開始前エラーを返せます。`startsAt` は種類の締切時刻ではありません。
4. `/` に `day: 0` の状態が出たら、`daySteps[0]` ステップ分の全行動を締切 `endsAt` までに提出します。
5. 翌日の状態が公開されたら `daySteps[day]` を使います。残燃料と位置はサーバーから受け取った状態を基準にします。集計・公開の遅延を考慮し、同じ日を重複処理しません。
6. 最終日の後は `/` と `/setting` が時間外になることがあります。

簡易サーバーで確認した時間外メッセージは `match has not started`、`agent kind submission is closed`、`match has ended` でした。これは実装確認の記録であり、全本番環境のメッセージを保証する列挙ではありません。403だけで試合終了とみなさず、どのAPIで、いつ発生したかを確認します。

有効な種類が時間内に届かない場合は全車巡回車、有効な行動が届かない日は全車が終日待機となります。再提出で不受理になっても、それ以前の有効な回答を失ったとは扱いません。通信失敗で提出結果が不明な場合は、必ず同じ日の締切と最新状態を再確認します。POSTを無制限に自動再送すると日付をまたいで別日に送る危険があるため、送信は日・締切に結び付けます。

Q42の目安は**秒間約5リクエスト**です。設定取得、状態取得、種類提出、行動提出を合わせて制限します。タイムアウトや429、5xxには間隔を空け、認証・不正形式のエラーを繰り返し送信しない設計にします。

## 座標・行動

`pos = y * width + x`、`x = pos % width`、`y = pos // width` です。左上が0で、行ごとに右へ増えます。マップはトーラスではありません。0始まりの**偶数行が右へ半セルずれます**。方向と隣接先は以下の通りです。

| 値 | 方向 | 偶数行 `(dx,dy)` | 奇数行 `(dx,dy)` |
|---|---|---|---|
| 0 | 左上 | `(0,-1)` | `(-1,-1)` |
| 1 | 右上 | `(1,-1)` | `(0,-1)` |
| 2 | 右 | `(1,0)` | `(1,0)` |
| 3 | 右下 | `(1,1)` | `(0,1)` |
| 4 | 左下 | `(0,1)` | `(-1,1)` |
| 5 | 左 | `(-1,0)` | `(-1,0)` |

負数 `-n` は地形によらず `n` ステップの待機です。待機中に燃料は消費しません。移動命令は1要素ですが、移動**元**の地形・道路状態に応じたステップ数を消費します。

| 地形値 | 地形 | 移動ステップ | 巡回車の燃料 |
|---|---|---|---|
| 0 | 平地 | 2 | 1 |
| 1 | 道路・順調（status 0） | 1 | 2 |
| 1 | 道路・混雑（status 1） | 2 | 2 |
| 1 | 道路・渋滞（status 2） | 4 | 2 |
| 2 | 山地 | 3 | 2 |
| 3 | 池 | 進入不可 | — |

全エージェントの行動時間がそれぞれ `daySteps[day]` と完全一致する必要があります。マップ外、池、燃料不足、時間不足を1エージェントでも含むと全体が不受理です。移動の途中で日が終わる計画は不可です。足りない時間は最後の待機で埋めます。補給車も移動時間は同じですが、移動に燃料を消費せず、巡回車へ無限に補給できます。

## シミュレーションの時点

ステップ0は次の行動を予約するだけです。ステップ1から最終ステップNまでは以下を処理します。

1. 完了する移動の燃料を消費。
2. 完了する移動の到着位置を反映。
3. 現在地がスポットの巡回車がうどんを獲得。
4. 自チームの補給車と同じセルの巡回車を上限まで補給。
5. 交通量を更新（移動反映後の滞在位置を集計。下記の資料間の相違に注意）。
6. N未満であれば、完了した行動の次の行動を予約。

複数ステップかかる移動の途中では、エージェントはまだ移動元にいます。その間もうどんの獲得と燃料補給が起こり得ます。**燃料の十分性は移動開始時だけで判定してはいけません。** 公式簡易サーバーでは、移動開始時には不足していても、移動完了前に移動元で補給されれば受理されました。

確認例: 上限2の巡回車が山地セル1に燃料1でいるとき、右へ3ステップの移動を指定。隣の平地セル2にいた補給車が左へ2ステップでセル1に来ると、ステップ2で巡回車へ補給し、ステップ3で巡回車が燃料2を消費してセル2に到着できます。

巡回車は同一スポットから1日1玉まで獲得できます。日ごとに取得済み状態と在庫はリセットされます。各チームの在庫は独立です。同時に在庫を超える巡回車が到達すると、初期リストで若いエージェントから獲得します。補給車はうどんを獲得しません。各日のステップ0では獲得・補給は起きません。開始時点でスポットにいる車も、ステップ1以降にその場にいれば獲得します。

**交通量についての資料間の相違:** 問い合わせ回答2 Q27 の文章は「移動前」としています。一方、競技補足資料の表と配布簡易サーバーは移動反映後の位置を集計します。実測例では、道路セル0から最初の1ステップで平地へ移り、残り2ステップ待機すると、混雑基準値1でも翌日の道路セル0は順調（滞在数0）でした。移動前なら滞在数1で混雑になるため、クライアントの交通量予測は配布サーバーと補足資料に合わせて移動後を採用します。本番の道路状態は配布された値を常に優先します。

道路状態は日内で固定され、各日開始時に提供されます。交通量の実数は提供されません。前日と前々日の全チームの道路滞在ステップ数の合計をチーム数で割り、混雑・渋滞基準値と比較します。初日は全道路が順調、翌日は前日分のみです。クライアントは翌日の交通予測よりも配布された `traffics` を優先します。

勝敗は、試合全体の系列種類数、日ごとの系列種類数の合計、獲得玉数、最後の有効回答までの時間の合計、の順です。画面上の獲得数や得点は通信APIに含まれないため、クライアントで表示する場合は予測値として区別する必要があります。

## 公式簡易サーバーでの確認

配布物の実行ファイルはこのリポジトリには含めません。対応する実行ファイルと設定JSONを指定して起動できます。

```sh
./procon-server-darwin-arm64 \
  -config example.json \
  -addr 127.0.0.1:8080 \
  -kind-deadline 5s \
  -match-start-delay 5s
```

Linuxは `procon-server-linux-amd64`、Intel Macは `procon-server-darwin-amd64`、Windowsは `procon-server-windows-amd64.exe` を使います。起動から種類締切までの既定値は5秒、その後の試合開始までの既定値も5秒です。`-addr` の指定がなければ `PORT` 環境変数、さらに未設定なら `:8080` です。

2026年10月27日に配布済みdarwin-arm64バイナリをlocalhostで起動し、設定取得、種類受付・締切、初日状態、待機計画受理、不正行動の負revision、有効計画再提出、終了後403、移動中の補給、他チームの補給車は自チームへ補給しないこと、交通量は移動反映後の位置を使うことを確認しました。これは提供された簡易版に対する互換性確認であり、実大会サーバーに接続した確認ではありません。

サーバー設定JSONのトップレベルは `{ "problem": {...}, "teams": [...] }` です。`problem` 内では `map` ではなく `width`, `height`, `cells` を直接持ち、初期位置は `agentStarts`、参加チームの認証は `teams[].token` に入ります。`GET /setting` の応答形式とは区別してください。

結合テストは配布バイナリのパスを明示した場合だけ実行されます。通常のテストではスキップされます。

```sh
HEXA_OFFICIAL_SERVER=/absolute/path/procon-server-darwin-arm64 \
  python3 -m unittest discover -s tests -p test_official_integration.py -v
```

4件の結合テストで、CLIの全日自動提出、生成計画の受理と翌日の位置・燃料の一致、不受理の再提出が有効回答を上書きしないこと、移動途中の補給、移動後の交通量集計を検証します。テストには一時ファイル内の合成マップとテスト専用トークンだけを使います。
